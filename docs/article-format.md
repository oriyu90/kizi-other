# kizi AI article format v2

この文書は、AIがkiziの記事をMarkdownで作成し、投稿アプリが検証・HTML変換・振り分け・公開するための共通契約です。AIにはこの文書全体を渡し、完成したMarkdownを1ファイルだけ出力させてください。

## 1. ファイルと記事ID

- 1記事につき `content/articles/<記事ID>.md` を1ファイルだけ作る。
- 記事IDは `YYYY.M.D.N`。`N` はその公開日の何本目かを表す1始まりの整数。
- 例: 2026年8月21日の1本目は `content/articles/2026.8.21.1.md`。
- ファイル名、front matterの `id`、公開HTML名、カタログIDを完全に一致させる。
- Markdownを唯一の編集元とし、生成済みHTMLを手で直さない。

## 2. AIへの出力指示

AIは説明、前置き、コードフェンスを付けず、次の形式のMarkdown本文だけを出力します。

```markdown
---
schemaVersion: 2
id: "2026.8.21.1"
issue: 2
title: "記事タイトル"
subtitle: "記事の視点を示す短い副題"
description: "トップページと検索結果に使う、全角70〜120字程度の要約。"
publishedAt: "2026-08-21"
updatedAt: "2026-08-21"
order: 1
author: "kizi編集部"
language: "ja"
categories:
  - engineering
  - science
tags:
  - 資源開発
  - 地質
readingMinutes: 10
heroPool: engineering
status: draft
---

## 要点

- 最重要の結論を1文で示す。
- 根拠となる事実を示す。
- 未確定事項や限界を示す。

## 最初の論点を表す見出し

本文を書く。主張と事実、確認済み事項と推測を混同しない。

### 必要な小見出し

詳しい説明を書く。

## 結論

記事全体の答えと、現時点で残る不確実性を簡潔にまとめる。

## 出典

- [資料名](https://example.com/source) — 発行元、公開日または参照日
```

## 3. 必須メタデータ

| 項目 | 型・条件 | 用途 |
| --- | --- | --- |
| `schemaVersion` | 整数 `2` | 変換仕様の判定 |
| `id` | `YYYY.M.D.N` | ファイル名・URL・保存機能の共通キー |
| `issue` | 1以上の整数 | 画面上の Issue 番号 |
| `title` | 1行、原則60字以内 | H1、一覧、OGP |
| `subtitle` | 1行、原則80字以内 | 記事冒頭の副題 |
| `description` | 1行、全角70〜120字程度 | トップの短い説明、SEO、SNS |
| `publishedAt` | `YYYY-MM-DD` | 公開日 |
| `updatedAt` | `YYYY-MM-DD` | 最終更新日。初版は公開日と同じ |
| `order` | 1以上の整数 | 同日の掲載順。ID末尾と一致 |
| `author` | 1行 | 著者名 |
| `language` | `ja` | 原稿の基準言語 |
| `categories` | 1〜5個の配列 | 先頭を主ジャンルとして表示と画像選択に使う |
| `tags` | 1〜8個の日本語配列 | 記事の具体的な主題 |
| `readingMinutes` | 1以上の整数 | 読了時間表示 |
| `heroPool` | 許可ジャンル1つ | 共通トップ画像プール |
| `status` | `draft` または `published` | 公開制御 |

許可するジャンルIDは次の5つだけです。

- `culture`: 文化
- `economy`: 経済
- `engineering`: 工学
- `politics`: 政治
- `science`: 理学

`heroPool` は `categories` の先頭と一致させます。工学版への振り分けは、先頭だけでなく `categories` のどこかに `engineering` があるかで判定します。

## 4. 本文構造

- タイトル、副題、説明はfront matterに置き、本文に `#` のH1を重複させない。
- 本文は必ず `## 要点` から始め、3〜5項目の箇条書きにする。
- 本論は内容を表す `##` 見出しで分け、必要な場合だけ `###`、`####` を順番に使う。
- 最後の本論見出しを `## 結論`、末尾を `## 出典` とする。
- 段落、順序なし／順序付きリスト、引用、表、強調、リンク、インラインコード、コードブロックを使用できる。
- 表は列を増やしすぎず、スマートフォンでも意味が伝わる見出しにする。
- 本文中のリンク文字列は「こちら」ではなく、リンク先の内容が分かる名称にする。

## 5. 編集・検証ルール

- 要点、タイトル、副題、説明は本文と矛盾させない。
- ニュース記事として、確認済みの事実、当事者の主張、分析・推測を明確に区別する。
- 数値には単位と対象期間を付ける。異なる統計を比較するときは定義差を書く。
- 未来予測や因果関係を断定しない。根拠が弱い場合は不確実性を明記する。
- 実在しない出典、URL、引用、数値を作らない。確認できない情報は本文から除くか、未確認と明記する。
- 直接引用は必要最小限にし、主に要約で記述する。
- 出典一覧には資料名、URL、発行元、公開日または参照日を付ける。
- 日本語原稿が正本。投稿アプリは同じ記事IDのHTML内へ英語、ポルトガル語、ドイツ語、簡体字中国語、アラビア語の翻訳を生成できるが、別の手編集記事ファイルは作らない。

## 6. 禁止するMarkdown

- `![代替テキスト](画像URL)` を含む本文画像
- raw HTML、`iframe`、`script`、外部埋め込み
- Mermaidなど、実行時JavaScriptを必要とする独自記法
- H1の重複、見出しレベルの飛び越し、空の見出し
- front matter外の管理用メモ、AIの作業説明、読者向けでないプロンプト

図が必要な情報は、原則として表、リスト、通常の文章へ変換します。サイトの画像は記事本文には置かず、ジャンル別の共通トップ画像だけを使います。

## 7. 投稿アプリが生成・更新するもの

投稿アプリはMarkdownを読み、公開時に次を同じ処理で更新します。

1. front matterと本文構造を検証する。
2. `categories` によって配信先を1つに決める。
3. `website/articles/<ID>.html` を生成する。
4. `website/articles/index.json` を更新する。
5. 記事版のトップページ、RSS、サイトマップと、記事HTML内のcanonical、OGP、JSON-LDを更新する。
6. リンク、翻訳、トップ画像プール、1記事1ファイルを検証する。
7. 対象記事リポジトリの`main`へ1コミットで反映する。
8. GitHub Actionsが変更された記事HTMLと版カタログをR2へ同期し、`kizi.pages.dev`の公開URLを有効化する。

配信先は次の通りです。

- `categories` に `engineering` を含む: 正本は`oriyu90/kizi-kougaku`
- `categories` に `engineering` を含まない: 正本は`oriyu90/kizi-other`
- どちらも読者向け公開URLは`https://kizi.pages.dev/articles/<ID>`

## 8. 公開前チェック

- ファイル名、`id`、日付、`order` は一致しているか。
- `categories` と `heroPool` は許可値か。
- 要点は本文の答えを3〜5項目で要約しているか。
- 結論と出典があるか。
- 本文画像、raw HTML、架空の出典がないか。
- 工学／非工学の両方へ重複していないか。
- `npm run check` が成功するか。
